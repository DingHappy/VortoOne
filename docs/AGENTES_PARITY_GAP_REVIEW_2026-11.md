## 2. 最容易混淆的六件事

1. **两边都有 Workspace 一类入口，但含义不同。** 上游的 organization/workspace 是账号、真人成员、
   Agent、频道和数据权限的共同边界；VortoOne 当前每个运行端先一个个人空间，内部管理多个登记项目。
   切电脑、切项目不等于同一服务支持多人、多租户 Workspace。
2. **上游 Roles 主要是“真人成员的职务/权限”，本仓岗位主要约束 Agent 工具。**
   上游另有 Agent 的资源访问树。不能把两个叫法相似的登记直接互换。
3. **本仓已有频道，但它是带话题元数据的原 SID 会话。** 不等于上游带真人/Agent 成员、
   公私可见性、未读、@提及和线程的协作频道。
4. **本仓已有账号、会员和模型接入。** 缺少的是上游那套 Workspace 成员/席位/用量/连接归属等产品组合，
   不能笼统写成“我们没有账号或付费入口”。
5. **上游 Cloud 不是一份前端代码即可获得的服务。** 开源仓库有计费链接、额度和托管接入合同；
   当前 billing 路由明确把计划、价格、币种交给外部计费服务。模型、OAuth、推送和云电脑也各有部署前提。
6. **同一公司三个人共享 Workspace，不等于三个独立私有助理跨主机互联。**
   上游原生支持前者；不能由此声称后者已经现成可用。原先保留的“助理互通”方向仍需单独定交付和共享边界。

## 11. 不应随界面一起丢掉的 VortoOne 能力

这些不是“比上游多或更安全”的结论，而是本仓已经明确承诺的合同，迁移时必须映射或另行决定：

- 一个 runtime、共同工具运行层、来源/污点和主人确认；界面不可自行绕过。
- 隔离开发副本、验证与交付、原任务台账、检查点/问题/验收及来源绑定。
- 主人设备的签名写入与普通卡限制；设备登录、模型账号和资料共享不混为授权。
- 私人来源与联网岗位的组合规则、部门笔记的出处与批准、专员禁用动作。
- 原费用/用量的未知状态、原恢复与无人值守默认拒绝，不从图标或“已结束”推断通过。
- 外部执行器的原生权限与会话语义、已退役用户 CLI 的内部启动兼容路径。
- 旧数据的读取、迁移和返回路径；不能为获得相同页面而静默删除记录。

若主人选择改变其中任一项，应先明确新合同及兼容范围，再进入实现。
