## 2. 现状

`LOCAL_RESIDENT.md` 和 `runtime-hosting.md` 记录了三种运行方式：Desktop 本机引擎、这台 Mac 的常驻助手、另一台电脑的常驻助手。它们共用同一套运行层，但产品上有四个缺口：

1. **资料分家。** 本机和远端各留自己的聊天和配置，不同步、不合并。切换连接等于换了一个助理。
2. **远端只有脑，没有手。** 连到常驻电脑后，执行都发生在那台机器上，够不到这台 Mac 的文件和项目。只有「让助理查看 Codex」这一条单向上报（`OBSERVATION_ORDER.md`）。
3. **接入门槛高。** 手机要公网域名、证书和反向代理。Desktop 与引擎的协议版本要求完全相等（`desktop/src/gateway.ts` 的 `DESKTOP_PROTOCOL_VERSION`），一边升级另一边就连不上。
4. **只认一个主人。** 确认门只区分「问不问得到真人」（`src/agents/gate.py` 的 `can_ask_human`），不区分是哪个人。

## 3. 家：三个位置，同一个程序

**家**是保存聊天、记忆、角色、定时和审批的那一个服务实例。三个位置跑同一份程序，差别只在放在哪、谁来维护。

| 位置 | 谁维护 | 适合 | 限制 |
| --- | --- | --- | --- |
| 这台电脑 | Desktop 安装并管理（现有的本机常驻助手） | 个人空间 | 关机或休眠时不工作；别人和手机要另开接入才连得进来 |
| 一台常开的电脑 | 用户自己，用一条安装命令 | 个人空间、小团队 | 用户要自己升级和备份 |
| 云端 | 我们 | 团队空间、不想自己维护的人 | 用户资料在我们的机器上；有持续成本 |

规则：

- 一个空间只属于一个家。个人空间和团队空间按对齐清单 D03 相互隔离，可以在不同的家里。
- 团队空间不建议放在「这台电脑」：主人关机，所有成员都断线。首次引导里对这个组合给出提示，不禁止。
- 换位置是**搬家**：在旧的家导出，在新的家导入，旧的家停用。导出包含聊天、记忆、角色、定时和任务台账；凭据和模型密钥不随包导出，在新的家重新连接。不做两个家之间的持续同步。
- Desktop 本机引擎（随 App 退出的那个子进程）保留给项目工作区，不再作为助理的家。

## 4. Desktop：地址列表与首次引导

- Desktop 保存一份「家的列表」和当前选中的那一个。每个家的登录状态和缓存分开存。切换就是换一个地址，不迁移任何资料。
- 首次引导先问「放在哪」，三选一。云端在第 6 节完成前显示为「即将提供」。
- 找到已有的家靠三处，不扫描局域网：本机的登记文件、账号服务里登记在本账号下的家（`ACCOUNT_SERVICE_DESIGN.md` 第 3 项）、手填地址。
- 除本机回环地址外一律要求加密连接。
- 协议版本改为区间兼容：家声明自己支持的最低和最高版本，Desktop 在区间内即可连接；不兼容时明确提示哪一边需要升级，不再表现为连接失败。

## 5. 连接的电脑

让放在别处的家能在一台指定的电脑上执行，而不要求那台电脑开放任何入口。

### 5.1 连接方式

- 被连接的电脑上跑一个连接器，由它主动向家拨出长连接。电脑一侧不开端口、不需要公网地址。
- 配对：有权的人在家里生成一次性配对码（短时有效、只能用一次、只存哈希），连接器用它换一个机器令牌，令牌只保存在那台电脑上。在家里移除这台电脑，令牌立即失效并断开连接。
- 连接器随 Desktop 一起安装和升级；家在本机时自动配对本机，不需要人操作。
- 断线后连接器退避重连。执行中的长任务脱离连接继续运行并在本地记日志，重连后补报结果；不自动重发已经开始执行的动作。

### 5.2 安全边界

这是本设计里攻击面最大的部分，实施前要单独写一份 ADR。

- **判定只在家里做。** 确认门、污点、能力档案、沙箱策略都在家里执行，连接器只执行已经放行的调用，不自己决定放行。
- **连接器是第二道闸，不是第一道。** 它在本地再核对一次：调用是否落在这台电脑主人打开的能力和文件夹范围内，超出即拒绝。家被攻破时，损失以这份本地范围为上限。
- **默认关。** 新配对的电脑没有任何文件夹权限，命令执行关闭。每项能力（读文件、写文件、命令、浏览器、Codex）由这台电脑的主人在本机的设置里逐项打开，家里的页面不能替他打开。
- **回传的内容按外部内容处理。** 命令输出、文件内容、页面文字进入对话时带出处标记，按现有污点规则计入。
- **凭据不出电脑。** 那台电脑上已有的登录（编码助手的账号、SSH 钥匙）留在原地使用，不上传到家里。家里的凭据也不下发到连接的电脑。
- **电脑归配对的人。** 默认只有配对人发起的回合可以在上面执行。要给团队用，必须由配对人在本机明确打开，可随时收回。H2 的开关不能越过这一条。

### 5.3 可以复用的现有部分

- 执行入口：`agents/tool_runtime.py` 的可信宿主调用（`TOOL_RUNTIME.md`）。连接的电脑作为一种执行目标接在工具运行层之下，不新建第二套工具系统。
- 观测与回执：`agents/backends/execution.py` 的执行引用与快照、`observation_order.py` 的有序上报。
- 身份登记：`gateway/account_registration.py` 的实例归属与撤销。

## 6. 云端

- **每个用户一个隔离实例。** 和「常开的电脑」跑同一个镜像，由账号服务负责开通、登记、暂停和回收。不把现有的单主人、文件落盘的状态改写成多租户：那等于重写存储并重新论证整个安全内核。
- **云端实例没有用户的电脑。** 它能做的是对话、记忆、定时、联网查资料和已连接的外部服务。要操作用户的文件和项目，必须配对一台连接的电脑（第 5 节）。所以云端排在连接的电脑之后。
- **上线前提：**
  1. 模型配置和外部凭据迁到受保护的存储，不再明文落盘（`CURRENT_ARCHITECTURE.md` 已记为未完成项）。
  2. 实例之间在进程、文件系统和网络上相互隔离，并有一份越界测试。
  3. 备份、恢复和删除账号时的资料清除流程。
  4. 对外说明里写清楚：云端的资料存在我们的机器上。
- 计费不进运行层。沿用账号服务的边界：钱的账只在中转站，运行层只接受「暂停 / 恢复」这类结果。
- 成本：每人一个实例比多租户贵。先按少量用户验证，用户数上来后再评估是否值得改存储。

## 7. 多人：频道、身份与授权

### 7.1 怎么交流

所有成员连到同一个家，在频道和私聊里交流。和家放在哪无关。频道沿用 `DESKTOP_CHANNELS.md` 的会话元数据，团队空间里增加成员关系和可见范围。

### 7.2 身份

- 成员表只记两种身份：**所有者**和**成员**。所有者不是一个可配置的岗位，而是身份；一个团队空间至少保留一个所有者。
- 其余权限用**单项授权**表达：所有者把某一项能力授给某个成员，可以限定范围（哪些角色、哪些连接、哪类动作）。
- 先不做可叠加的自定义岗位。团队成员多到单项授权管不过来时再加，届时岗位只是一组授权的打包，检查方式不变。

### 7.3 权限表

| 能做的事 | 所有者 | 成员 | 可授权给成员 |
| --- | --- | --- | --- |
| 在频道发言、和角色对话、建频道 | 是 | 是 | |
| 建自己的 AI 角色、连接自己的电脑和模型账号 | 是 | 是 | |
| 邀请和移除成员 | 是 | 否 | 是 |
| 管理别人建的角色、团队的连接和凭据 | 是 | 否 | 是 |
| 审批团队资源上的动作 | 是 | 否 | 是，可限定范围 |
| 给角色设 AI 代批等级（对齐清单 D04-3） | 是 | 否 | 是，仅限自己有权审批的范围 |
| 给角色打开「代成员办事」（第 8 节） | 是 | 否 | 是，仅限权限不超出自己的角色 |
| 查看用量和审计 | 是 | 否 | 是 |
| 给别人授权 | 是 | 否 | 只能授出自己有的 |
| 删除空间、转让、搬家、导出、计费 | 是 | 否 | 不可授权 |

### 7.4 固定规则

以下规则放在安全内核一处，各端只声明身份，不各写一遍。

1. **审批回到资源的主人。** 动的是谁的东西就问谁，不问发消息的人。个人资源问本人；团队资源问所有者或在该范围内被授权的成员。
2. **个人空间对其他人不可见。** 包括团队所有者，也不因任何授权而放开。
3. **谁都不能授出自己没有的。** 授权、建角色、改角色权限时都核对操作人自己的权限。
4. **无人值守按创建人算。** 定时和事件触发的回合用创建人当时有效的权限；创建人离开或被移除，这些任务暂停，等有权的人接手，不自动转给别人。
5. **权限变更由真人确认。** AI 只能提议，不能修改自己或别人的权限、代批等级和第 8 节的开关。
6. **离开即撤销。** 成员被移除后，他的会话、配对的电脑、授出的范围立即失效；他建的角色交给所有者，不删除。

## 8. 回合权限：按发起人封顶，可按角色打开

一个回合能做什么，由三样东西决定：角色登记的权限、发起人的权限、这个角色的「代成员办事」开关。

| 开关 | 回合的有效权限 | 审批发给谁 |
| --- | --- | --- |
| 关（默认） | 角色的权限与发起人的权限取交集 | 资源的主人 |
| 开 | 角色的权限，不看发起人 | 资源的主人，不发给发起人 |

说明：

- **默认关。** 新建的角色、从个人空间共享进团队的角色都是关。
- **按角色开，不按团队一把开。** 团队可以设一个新角色的默认值，但每个角色单独记录，界面上能看到哪些角色开着。
- **谁能开。** 所有者；或者被授予「管理角色」的成员，且该角色的权限不超出他自己的权限。否则他等于通过开关给自己加了权限，违反 7.4 第 3 条。
- **开了也越不过的：** 个人空间（7.4 第 2 条）；连接的电脑的配对人限制（5.2）；`STAFF_DESIGN.md` D4 规定永远由真人完成的动作；污点规则；无人值守默认拒绝。
- **开关本身的变更写审计**，记录谁在什么时候对哪个角色开或关；关闭立即生效，正在执行的回合在下一次工具调用前重新核对。
- 开着的时候，发起人自己不能批准这次动作，除非他本来就有该范围的审批权。

举例：小李不能动团队的发布流程。「发布助手」角色有发布权限。开关关着时，小李让它发版会被拒绝并说明原因；开关开着时，它会发起发布，但审批卡发给所有者或有发布审批权的人，小李只能看到结果。

## 9. 对安全内核的改动

现有内核假定只有一个主人。多人之后要补的是「是谁」这个维度，不是另写一套规则。

- **确认门**（`agents/gate.py`）：判定输入增加发起人身份和所属空间；「问得到真人」细化为「问得到这次该问的那个人」。问不到时仍是拒绝，不退化成问发起人。
- **能力档案**（`agents/capabilities.py`）：新增成员发起的回合对应的档案，上限由第 8 节的有效权限给出；现有 local、external、unattended、owner_device 四档的含义不变。
- **污点**（`agents/taint.py`）：按 H8，团队成员的发言作为已登录真人的输入，不单独触发污点；外部内容的规则不变。没有选的另一种做法是把非主人的发言一律按外部内容标记，那样团队角色实际上只能读、不能替人办事。
- **记忆写入策略**（`memory/write_policy.py`）：成员的发言不能直接写进别人的个人记忆；团队记忆的写入按空间归属判定。
- **契约测试**：`tests/unit/test_three_end_contract.py` 的能力矩阵增加「发起人身份」一列；`test_layering.py` 的分层名单不放宽。

这部分要先于团队频道上线，并各自对应一份 ADR。

## 10. 落地顺序

每步一个或一组 PR，前一步合并并验收后再开下一步。

| 步 | 内容 | 依赖 | 验收 |
| --- | --- | --- | --- |
| 1 | 家的列表、首次引导三选一（云端置灰）、本机常驻助手作为「这台电脑」的家、搬家的导出与导入 | H3 | 本机与一台常开的电脑之间切换不丢会话；搬家后旧的家停用 |
| 2 | 一条安装命令与镜像、家的自升级与回滚、协议区间兼容 | 步 1 | 在一台全新的主机上按文档装好并被 Desktop 连上；Desktop 先升级时仍能连接 |
| 3 | 连接的电脑：配对、能力开关、执行、断线恢复 | H4，步 2，单独的 ADR | 放在别处的家能在这台电脑的指定文件夹里读写；未打开的能力被本地拒绝 |
| 4 | 内核带上发起人身份；所有者与成员、单项授权；第 8 节的开关 | H7、H8，单独的 ADR | 能力矩阵契约测试覆盖成员发起的回合 |
| 5 | 团队频道与成员管理界面 | 步 4 | 两个账号在同一个团队空间里按第 7、8 节的规则被放行或拒绝 |
| 6 | 云端：按账号开通实例 | H5，步 2、3，6 节的四个前提 | 两个账号的实例相互不可见；删除账号后资料清除 |

步 1 到步 3 只涉及个人使用，可以不等多人部分。步 4 和步 5 可以与步 3 并行设计，但不并行上线。

## 11. 不做的事

- 不做两个家之间的资料同步或合并。
- 不把运行层改成多租户。
- 不让家主动连入任何人的电脑。
- 不在连接的电脑上保存家里的凭据，也不把那台电脑的登录上传。
- 本轮不做访客身份和可叠加的自定义岗位。
- 不因为页面上有某个位置的入口，就对外承诺对应的服务已经提供。
